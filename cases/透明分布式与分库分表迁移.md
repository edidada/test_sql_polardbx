# 透明分布式与分库分表迁移 — PolarDB-X（好想来零食量贩）

> 本案例对应 `.github/workflows/transparent_sharding.yml` 与 `sql/transparent_sharding.sql`，
> 所有 SQL 已在 GitHub Actions 的 PolarDB-X 容器中实际执行验证。

## 背景

好想来（零食量贩）早期为支撑业务增长自建分库分表，并把分片规则 `shard = user_id % N`
直接写死在业务代码里。随着门店与订单量增长，问题集中暴露：

- **强耦合**：每张物理表都要在代码里硬编码表名与路由公式，业务 SQL 到处是 `UNION ALL`。
- **运维困难**：加字段、改索引要逐张表执行；跨分片查询、聚合都要手工拼装。
- **扩容痛苦**：从 4 分片扩到 8 分片，需新建表、迁移历史数据、改分片规则并随业务代码一起发版。

## 解决方案：迁移 PolarDB-X，用透明分布式解耦

| 维度 | 迁移前（应用层分库分表） | 迁移后（PolarDB-X 透明分布式） |
|------|--------------------------|-------------------------------|
| 分片规则位置 | 写在业务代码里（`user_id % 4`） | 收敛到 DDL（`PARTITION BY HASH(user_id)`） |
| 写入路由 | 代码计算分片号后拼表名 INSERT | 只写逻辑表，内核自动路由 |
| 点查 | 先算分片再拼表名 | `WHERE user_id = ?` 透明路由 |
| 全局统计 | 代码 `UNION ALL` 所有分片再聚合 | 一条 SQL，内核透明聚合 |
| 跨分片 JOIN | 代码逐分片查询再内存归并 | 广播表 + 内核透明下推 |
| 扩容 4→8 | 建新表 + 数据重分布 + 改代码发版 | `ALTER TABLE ... PARTITIONS 8`，在线变更，代码零改动 |

## 关键 SQL

```sql
-- 分片规则写在 DDL，而非业务代码；复合主键包含拆分键以保证全局唯一
CREATE TABLE orders (
  id BIGINT,
  user_id BIGINT NOT NULL,
  store_id INT,
  amount DECIMAL(10,2),
  created_at DATETIME,
  PRIMARY KEY (id, user_id)
) PARTITION BY HASH(user_id) PARTITIONS 4;

-- 业务代码只写逻辑表，无需关心分片
INSERT INTO orders VALUES (1004, 4, 101, 25.50, NOW());
SELECT COUNT(*), SUM(amount) FROM orders;          -- 透明聚合
EXPLAIN SELECT * FROM orders WHERE user_id = 4;    -- 透明路由下推

-- 在线扩容：改分区数即可，数据自动重分布，业务代码零改动
ALTER TABLE orders PARTITION BY HASH(user_id) PARTITIONS 8;

-- 维度表广播，跨分片 JOIN 透明下推
CREATE TABLE dim_store (store_id INT PRIMARY KEY, store_name VARCHAR(50)) BROADCAST;
```

## 要点

- **分片规则收敛到 DDL**：`PARTITION BY` 描述数据分布，业务代码回归纯 CRUD。
- **复合主键包含拆分键**：分布式下 `PRIMARY KEY (id, user_id)` 保证全局唯一。
- **在线扩容**：`ALTER TABLE ... PARTITIONS` 由内核完成数据重分布，无需停机与改代码。
- **广播表**：小维度表用 `BROADCAST`，跨分片 JOIN 下推到各 DN 本地执行，避免跨分片数据搬迁。

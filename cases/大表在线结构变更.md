# 大表在线结构变更 — PolarDB-X（vivo TokuDB 归档库迁移）

> 本案例对应 `.github/workflows/large_table_ddl.yml` 与 `sql/large_table_ddl.sql`，
> 所有 SQL 已在 GitHub Actions 的 PolarDB-X 容器中实际执行验证。
> 场景取自 vivo 引入分布式数据库替代 TokuDB 归档库：400 亿行大表在 TokuDB 上几乎无法变更，
> 迁入后可在 2 小时 18 分钟内完成结构变更。本仓库以 PolarDB-X 演示同类在线 DDL 能力。

## 背景

TokuDB 解决了"存得下"（高压缩、低成本归档），但解决不了"管得好、变得动"：

- 400 亿行大表 `ALTER TABLE` 触发表拷贝与锁表，业务无法接受长时间停写。
- 加字段、加索引、改字段类型都要排期到低峰窗口，变更风险与成本极高。
- 这类集群应视为**需要规划下线的技术债**，而非长期依赖的基础设施。

## 方案：分布式在线 DDL

PolarDB-X 的大表 DDL 在线执行：通过双表拷贝 + binlog 增量同步 + 原子切换完成，
变更期间不阻塞读写，业务无感。

| 维度 | TokuDB（迁移前） | PolarDB-X（迁移后） |
|------|------------------|---------------------|
| 加字段 | 锁表 / 长时间拷贝 | `ADD COLUMN` 在线完成，不阻塞 DML |
| 加索引 | 停写建索引 | 在线建全局二级索引 |
| 改字段类型 | 几乎不可行 | `MODIFY COLUMN` 在线变更 |
| 数据一致性 | 手工校验 | 内核保证切换原子性，数据零丢失 |
| 400 亿行变更 | 难以完成 | 分布式并行，小时级完成 |

## 关键 SQL

```sql
-- 大表按 user_id HASH 拆分；复合主键包含拆分键保证全局唯一
CREATE TABLE orders_fact (
  id BIGINT,
  user_id BIGINT NOT NULL,
  store_id INT NOT NULL,
  amount DECIMAL(12,2) NOT NULL,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (id, user_id)
) PARTITION BY HASH(user_id) PARTITIONS 8;

ALTER TABLE orders_fact ADD COLUMN discount DECIMAL(10,2) NOT NULL DEFAULT 0.00;
ALTER TABLE orders_fact ADD INDEX idx_store (store_id);
ALTER TABLE orders_fact MODIFY COLUMN amount DECIMAL(14,2) NOT NULL;
-- 变更期间/变更后 DML 照常执行，数据不丢
```

## 要点

- **在线不锁表**：DDL 不阻塞读写，无需低峰停写窗口。
- **分布式并行**：DDL 任务下推到各 DN 并行执行，大表变更从"天级"降到"小时级"。
- **全局唯一约束**：拆分键必须包含在主键/唯一键中，故使用复合主键 `(id, user_id)`。
- **数据零丢失**：原子切换保证变更前后数据一致（CI 中断言行数与新增列均正确）。

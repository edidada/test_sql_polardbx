# 大表归档查询 — PolarDB-X（vivo TokuDB 归档库迁移）

> 本案例对应 `.github/workflows/large_table_archive_query.yml` 与 `sql/large_table_archive_query.sql`，
> 所有 SQL 已在 GitHub Actions 的 PolarDB-X 容器中实际执行验证。
> 场景取自 vivo 用分布式数据库替代 TokuDB 归档库：归档库不仅要"存得下"，还要"查得动、管得好"。

## 背景

归档库承载海量历史数据（百亿/千亿行），TokuDB 虽压缩率高、成本低，但：

- 跨年、跨月归档查询缺少分区裁剪，往往全表扫描，查询缓慢。
- 维护困难：索引、生命周期管理、冷热分层都缺乏分布式能力支撑。
- 存储成本低不等于可运营，"变得动、查得快"才是长期可依赖的标准。

## 方案：按时间分区 + 分区裁剪

PolarDB-X 按归档月份做 RANGE 分区，查询条件命中分区键时，内核自动裁剪，
只扫描目标分区，避免全量归档数据扫描。

| 维度 | TokuDB（迁移前） | PolarDB-X（迁移后） |
|------|------------------|---------------------|
| 数据分布 | 单库大表 | 按 `arch_month` RANGE 分区 |
| 单月查询 | 全表扫描 | 分区裁剪，只扫目标分区 |
| 跨年区间查询 | 全表扫描 | 只扫区间内分区 |
| 归档统计 | 全量聚合 | 分区内聚合，减少 IO |
| 生命周期管理 | 手工删表 | 分区级管理，新增/清理更清晰 |

## 关键 SQL

```sql
-- 拆分键 arch_month 必须包含在主键中
CREATE TABLE orders_archive (
  id BIGINT,
  user_id BIGINT NOT NULL,
  store_id INT NOT NULL,
  amount DECIMAL(12,2) NOT NULL,
  arch_month INT NOT NULL,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (id, arch_month)
) PARTITION BY RANGE(arch_month) (
  PARTITION p2023 VALUES LESS THAN (202401),
  PARTITION p2024 VALUES LESS THAN (202501),
  PARTITION p2025 VALUES LESS THAN (202601),
  PARTITION pmax  VALUES LESS THAN MAXVALUE
);

-- 分区裁剪: 只扫 p2024
EXPLAIN SELECT * FROM orders_archive WHERE arch_month = 202401;

-- 跨年区间: 只扫 2023/2024 分区
EXPLAIN SELECT COUNT(*), SUM(amount) FROM orders_archive
  WHERE arch_month BETWEEN 202301 AND 202412;
```

## 要点

- **分区裁剪**：查询谓词命中分区键 `arch_month` 时，只访问相关分区，大幅降低扫描量。
- **RANGE 分区归档**：按月份分区，历史数据天然分层，生命周期管理落到分区粒度。
- **全局唯一约束**：拆分键必须包含在主键中，故主键为 `(id, arch_month)`。
- **EXPLAIN 可验证**：CI 中打印执行计划，确认裁剪生效；并校验聚合结果正确。
